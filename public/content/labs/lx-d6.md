# 证书过期：MES 内网 HTTPS 握手失败

- 题目编号：`lx-d6`
- 所属模块：运维实操营 · Linux 服务器实操
- 题目类型：运维实操（终端实操，真实服务器执行命令）
- 难度 / 建议时长：进阶 / 10 分钟
- 文档路径：`public/content/labs/lx-d6.md`（站内地址 `/content/labs/lx-d6.md`）

> 本文同时服务两类读者：人（讲清这道题在练什么、环境要求、步骤、验收、常见错法）与站内 AI（据此生成准备与执行脚本）。AI 生成的脚本一律先预览、再由用户确认执行。

## 1. 题目目标与业务背景

**目标**：确认是证书过期而不是服务故障，找到证书文件与续期链路，续签并重新加载服务，恢复 HTTPS 访问。

**背景**：MES 内网访问地址 https://mes.factory.internal 由 nginx 终止 TLS，证书由公司 CA 签发，有效期 1 年，续期脚本每月 1 号跑一次。

**现象**：今天 08:00 全厂浏览器访问 MES 报「ERR_CERT_DATE_INVALID」，服务端日志却一切正常，业务同事以为 MES 挂了。

## 2. 涉及的数据表或服务

- nginx（TLS 终止）
- 公司 CA（签发证书）
- 续期脚本 /opt/mes/renew-cert.sh 与其 cron

## 3. 需要的账号与权限

- 需要 sudo：可读写 /etc/nginx/certs、可 reload nginx、可查 crontab 与 cron 日志
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置 nginx 站点 https://mes.factory.internal，证书已过期（notAfter 早于当前日期）
- 预置续期脚本与 cron，但脚本因 CA 配置路径失效而失败
- 预置 CA 私钥/证书与待签发 CSR，供演练重新签发
- 客户端测试用 curl（不带 -k）验证证书链可信

### 4.3 破坏性提示

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 5. 标准步骤

| # | 目标 | 参考动作 |
| --- | --- | --- |
| s1 | 确认服务本身是活的（先排应用层） | 先看服务状态，再 curl -k 绕过证书校验看 HTTP 是否通。 |
| s2 | 读证书有效期，确认是否过期 | openssl x509 -noout -dates 读证书有效期。 |
| s3 | 定位服务器上的证书文件与 nginx 引用 | 从 nginx 配置里找 ssl_certificate 路径，再 ls 证书文件。 |
| s4 | 查续期任务为什么没换证书 | 看续期 cron 与它的日志，确认是「任务没跑」还是「跑了但失败」。 |
| s5 | 修复续期链路并重新签发（先备份旧证书） | 备份旧证书 → 重新签发 → nginx -t 校验后 reload。 |
| s6 | 验证证书有效期与客户端访问都恢复 | 再读一次有效期，并用不带 -k 的 curl 验证证书链可信。 |

每一步的判定命令见第 6 节的验收正则。

## 6. 验收标准（可机器判定）

判分方式：终端实操逐条比对命令正则（任一条命中即通过该步），最终按通过步数给出评级。

| # | 步骤目标 | 命中的命令正则 |
| --- | --- | --- |
| s1 | 确认服务本身是活的（先排应用层） | `^systemctl\s+(status|is-active)\s+nginx` 或 `^curl\s.*(-k|--insecure)` 或 `^ss\s+-lntp` |
| s2 | 读证书有效期，确认是否过期 | `^openssl\s+x509` 或 `^echo\b.*\|\s*openssl` 或 `^openssl\s+s_client` |
| s3 | 定位服务器上的证书文件与 nginx 引用 | `^grep\b.*ssl_certificate` 或 `^ls\b.*\.crt` 或 `^ls\b.*\.pem` 或 `^find\b.*\.(crt|pem)` |
| s4 | 查续期任务为什么没换证书 | `^crontab\s+-l` 或 `^ls\b.*/etc/cron` 或 `^journalctl\b.*cron|^cat\b.*/var/log/cron` 或 `^systemctl\s+status\s+cron` |
| s5 | 修复续期链路并重新签发（先备份旧证书） | `^cp\b.*crt` 或 `^openssl\s+.*(req|x509)` 或 `^cat\b.*>.*\.crt|^cat\b.*>.*\.pem` 或 `^systemctl\s+reload\s+nginx` |
| s6 | 验证证书有效期与客户端访问都恢复 | `^openssl\s+x509` 或 `^curl\s.*https://` 或 `^systemctl\s+status\s+nginx` |

## 7. 常见错误与排查提示

- 确认服务本身是活的（先排应用层）：先看服务状态，再 curl -k 绕过证书校验看 HTTP 是否通。
- 要点：curl -k 返回 200 说明应用与反代都活着，故障在 TLS 层——这一步能省掉大量无用排查。
- 读证书有效期，确认是否过期：openssl x509 -noout -dates 读证书有效期。
- 要点：notAfter 已经早于当前日期——证书过期是硬事实，浏览器报错准确，不是客户端问题。
- 定位服务器上的证书文件与 nginx 引用：从 nginx 配置里找 ssl_certificate 路径，再 ls 证书文件。
- 要点：证书路径写在 nginx 配置里，先定位文件再谈续期，别在错误的位置折腾。
- 查续期任务为什么没换证书：看续期 cron 与它的日志，确认是「任务没跑」还是「跑了但失败」。
- 要点：cron 每月 1 号跑，日志显示 10-01 跑了但 failed——证书从没被换过，因为 CA 配置路径失效。
- 修复续期链路并重新签发（先备份旧证书）：备份旧证书 → 重新签发 → nginx -t 校验后 reload。
- 要点：换证书必须先备份旧证书，reload 前先 nginx -t；这样即使新证书有问题也能立刻回退。
- 验证证书有效期与客户端访问都恢复：再读一次有效期，并用不带 -k 的 curl 验证证书链可信。
- 要点：最终验收要两条都过：有效期在未来 + 不加 -k 也能访问成功。
- 不备份就覆盖证书：出问题无法回退
- 只 reload 不 nginx -t：语法错误会把整站反代打挂

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：curl -k 确认应用层 200、openssl 读证书有效期、nginx 配置中的证书路径
- 造故障：把服务端证书有效期设为过去日期，并让续期任务失败一次（写进日志）
- 记录回滚点：旧证书 .bak 副本、nginx 配置 .bak 副本

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- curl -k 验证应用层正常，先把范围收敛到 TLS 层
- openssl s_client | openssl x509 -noout -dates 确认证书过期
- grep ssl_certificate 定位证书文件，查 crontab 与续期日志找失败原因
- cp 备份旧证书 → 重新签发 → nginx -t → systemctl reload nginx
- 复测：有效期在未来 + 不带 -k 的 curl 返回 200

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。
- 失败处理：上游模型不可用 → 明确提示「AI 暂时不可用」，并保留手工执行入口；文档缺失 → 明确提示「该题文档缺失」；命令执行失败 → 原样回显报错行并停止该步；环境不符（例如题目要求 MySQL 却连的是 PostgreSQL）→ 在执行前就提示不匹配，不静默继续。
- 本题涉及的判据一律以第 6 节的机器判据为准，不采信模型自述的「已完成」。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
