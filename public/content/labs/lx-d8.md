## 1. 题目目标与业务背景

**目标**：从日志确认被拒的具体路径，修正属主/权限，让服务正常启动并验证。

**背景**：MES 报表服务 mes-report 以专用用户 report 运行，数据目录 /data/mes/report 由部署脚本创建。昨晚升级后服务被重启，今天起不来。

**现象**：systemctl status mes-report 显示 Failed，日志里是 Permission denied，业务报表页面打不开。

## 2. 涉及的数据表或服务

- mes-report.service（报表服务，运行用户 report）
- /data/mes/report（数据目录，属主错配）
- systemd（服务托管）

## 3. 需要的账号与权限

- 需要 sudo：可改 /data/mes/report 属主、可管理 mes-report.service
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置 mes-report.service（Unit 文件里 User=report）
- 预置 /data/mes/report 目录属主为 root 且其它用户无写权限（故障根因）
- 预置服务健康检查端口（如 8092）与日志目录
- 另有一个正常服务用于确认改动没有波及其它服务

| # | 目标 | 参考动作 |

## 6. 验收标准（可机器判定）

判分方式：终端实操逐条比对命令正则（任一条命中即通过该步），最终按通过步数给出评级。

| # | 步骤目标 | 命中的命令正则 |
| --- | --- | --- |
| s1 | 确认服务状态与失败原因 | `^systemctl\s+(status|is-active)\s+mes-report` 或 `^journalctl\b.*-u\s+mes-report` 或 `^cat\b.*mes-report.*\.log` |
| s2 | 查看被拒路径及其属主权限 | `^ls\b.*-ld` 或 `^ls\b.*-l` 或 `^stat\b` |
| s3 | 备份现状后修正属主 | `^cp\b` 或 `^ls\b.*>.*\.bak|^chown\b.*-R` 或 `^chown\b` |
| s4 | 重载并启动服务 | `^systemctl\s+daemon-reload` 或 `^systemctl\s+restart\s+mes-report` 或 `^systemctl\s+start\s+mes-report` |
| s5 | 验证服务真正可用 | `^journalctl\b.*-u\s+mes-report` 或 `^curl\s` 或 `^ss\s+-lntp` |

## 7. 常见错误与排查提示

- 确认服务状态与失败原因：systemctl status 看状态，journalctl -u 看日志原文。
- 要点：先拿到「哪条路径被拒」的原文，再动手改权限——直接 chmod -R 777 是事故的开始。
- 查看被拒路径及其属主权限：ls -ld 看目录属主与权限位，id 看服务跑在哪个用户下。
- 要点：服务用户是 report，目录属主是 root 且其它用户没有写权限——矛盾点就在这里。
- 备份现状后修正属主：备份单元文件后用 chown 把目录属主还给服务用户。
- 要点：用 chown 精确归还属主，而不是 chmod 777 放开所有人——最小权限原则在运维现场同样适用。
- 重载并启动服务：daemon-reload 之后 restart 服务。
- 要点：改完属主要重启进程才能拿到新权限：已经运行的进程仍然持有旧的凭据。
- 验证服务真正可用：看日志确认监听，再用 curl 打健康检查。
- 要点：active 只说明进程活着，接口 200 才说明业务可用。
- chmod -R 777 一把梭：把目录对所有人开放，属于安全事故源，站内危险清单会拦截
- 只改目录不改属主就重启：进程仍拿不到权限，必须 chown 到服务用户

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：systemctl status、journalctl -u 日志原文、ls -ld 目录、id report
- 造故障：把数据目录属主改成 root 并收紧权限，停止服务
- 记录回滚点：单元文件 .bak 与目录权限原文（ls -ld 输出留档）

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- journalctl -u mes-report 拿到被拒路径原文
- ls -ld + id 确认属主与运行用户矛盾
- 备份单元文件后 chown -R report:report 到数据目录
- systemctl daemon-reload + restart + is-active
- curl 健康检查确认接口 200

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
