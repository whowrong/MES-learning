## 1. 题目目标与业务背景

**目标**：按产线统计报废数、总产出数与不良率，不良率降序；不良率相同的产线按产线号升序，保证结果可复现。

**业务背景**：月度质量例会要按产线排不良率，名次并列时你希望报表顺序稳定：同一个不良率的两条产线，不能因为数据库返回顺序不同而在两次导出里换位置。

## 2. 涉及的数据表或服务

- 涉及表：`work_reports`、`work_orders`
- 练习库结构：内置练习库共 8 张表（items / bom / employees / equipment / work_orders / work_reports / inventory / sales_orders），合计约 231 行；真实连库时按第 4 节的空间与数据量建议预置同量级数据。

## 3. 需要的账号与权限

- 连接信息只保存在本站服务端（页面与仓库都不落明文密码），列表回显一律脱敏。

## 5. 标准步骤

```sql
SELECT w.line_code, SUM(r.qty_scrap) AS scrap_qty, SUM(r.qty_ok) + SUM(r.qty_scrap) AS total_qty, ROUND(1.0 * SUM(r.qty_scrap) / (SUM(r.qty_ok) + SUM(r.qty_scrap)), 4) AS scrap_rate FROM work_reports r JOIN work_orders w ON w.wo_no = r.wo_no GROUP BY w.line_code ORDER BY scrap_rate DESC, w.line_code ASC
```

- 思路提示：排序键写两个：不良率降序 + 产线号升序，并列行才有确定顺序
- 讲解：并列排序是报表最容易被忽略的细节：只写 ORDER BY scrap_rate DESC 时，两条不良率相同的产线谁先谁后由数据库自行决定，同一份数据两次导出的行序可能不同，客户比对时就会怀疑数据被改过。稳定的做法是补一个唯一的次级排序键（产线号、主键、工单号）。另外 1.0 * 分子 这种写法是为了避免整数除法把比率算成 0，ROUND 到 4 位再参与排序，可以避免浮点尾差把本该并列的两行排成不同名次。

## 6. 验收标准（可机器判定）

判分方式：执行下面的校验 SQL，结果必须与期望值完全一致（列名与行序都算）。

```sql
SELECT w.line_code, SUM(r.qty_scrap) AS scrap_qty, SUM(r.qty_ok) + SUM(r.qty_scrap) AS total_qty, ROUND(1.0 * SUM(r.qty_scrap) / (SUM(r.qty_ok) + SUM(r.qty_scrap)), 4) AS scrap_rate FROM work_reports r JOIN work_orders w ON w.wo_no = r.wo_no GROUP BY w.line_code ORDER BY scrap_rate DESC, w.line_code ASC
```

- 期望结果：`[["L2",27,165,0.1636],["L1",8,60,0.1333],["L4",37,497,0.0744],["L3",16,299,0.0535]]`

## 7. 常见错误与排查提示

- 常见错法：排序键写两个：不良率降序 + 产线号升序，并列行才有确定顺序
- 为什么：并列排序是报表最容易被忽略的细节：只写 ORDER BY scrap_rate DESC 时，两条不良率相同的产线谁先谁后由数据库自行决定，同一份数据两次导出的行序可能不同，客户比对时就会怀疑数据被改过。稳定的做法是补一个唯一的次级排序键（产线号、主键、工单号）。另外 1.0 * 分子 这种写法是为了避免整数除法把比率算成 0，ROUND 到 4 位再参与排序，可以避免浮点尾差把本该并列的两行排成不同名次。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一个可登录的数据库账号（MySQL / PostgreSQL / SQL Server，与题目要求一致）
- 对目标库表的建表、写入、删除权限（本题含删除 / 重建 / 清库类步骤）
- 一个可丢弃的练习用库：不要指向生产库

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 MySQL 8.0 容器（端口 14200-14249 段，现场生成；随机口令只回显一次，不落盘）
- 空库：建表 / 写入 / 索引重建类步骤可以从零做
- 容器内只有数据库本身，没有宿主机上的 systemd / nginx / 业务应用

- 最小组件配置：1 vCPU / 1 GiB 内存 / 2 GiB 可用磁盘（MySQL 8.0 实例约需 512 MiB 内存）
- 推荐配置：2 vCPU / 2 GiB 内存 / 5 GiB 可用磁盘（给 InnoDB 留 1 GiB buffer pool）

**模式 B 的限制：**

- 模式 B 的容器里只有数据库本身；依赖宿主机服务（systemd / nginx / 业务进程）的步骤请用模式 A。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
