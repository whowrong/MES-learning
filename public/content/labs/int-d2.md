# 报工高峰全员卡死：数据库阻塞排查

- 题目编号：`int-d2`
- 所属模块：运维实操营 · MES/ERP/WMS 集成排障
- 题目类型：运维实操（终端实操，真实服务器执行命令）
- 难度 / 建议时长：进阶 / 12 分钟
- 文档路径：`public/content/labs/int-d2.md`（站内地址 `/content/labs/int-d2.md`）

> 本文同时服务两类读者：人（讲清这道题在练什么、环境要求、步骤、验收、常见错法）与站内 AI（据此生成准备与执行脚本）。AI 生成的脚本一律先预览、再由用户确认执行。

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 1. 题目目标与业务背景

**目标**：在数据库层找到阻塞源头，安全解除，恢复报工，并落一条防复发的调度措施。

**背景**：MES 数据库为 MySQL（InnoDB），报工、工单、接口服务共用一个库。ERP 的报表账户 erp_report 有权直连该库取数。

**现象**：月末最后一天 16:30 报工高峰，车间终端全部转圈提交不了，MES 页面偶发 500；服务器 CPU 不算高、内存正常、磁盘不满。

## 2. 涉及的数据表或服务

- MySQL 8.0（MES 业务库）
- ERP 重报表长查询
- MES 报工接口

## 3. 需要的账号与权限

- 需要 sudo 管理服务；数据库账号需要 PROCESS 权限与 KILL 会话权限（仅演练账号授予）
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置 MES 业务库与一条长事务重报表查询（可用 SELECT SLEEP(600) 或大表全扫模拟）
- 演练账号需具备 PROCESS 与 KILL 权限，但不要给超级管理员账号
- 报工接口服务正常，用于验证阻塞解除后恢复

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 5. 标准步骤

| # | 目标 | 参考动作 |
| --- | --- | --- |
| s1 | 先确认数据库服务活着，排除宕机 | mysqladmin ping 是最快的存活探测。 |
| s2 | 查看当前所有连接与正在执行的 SQL，找异常长查询 | mysql -e "SHOW FULL PROCESSLIST"，重点看 Time 特别大的和 State 为 Waiting 的会话。 |
| s3 | 确认阻塞链：谁堵谁、堵了多少会话 | 查 sys.schema_table_lock_waits 或 performance_schema，MySQL 直接告诉你 blocking_pid 是谁。 |
| s4 | 评估后终止阻塞源头（报表可重跑，业务优先） | mysql -e "KILL QUERY 4213"。注意用 KILL QUERY（只杀这条 SQL、保留连接），并且杀之前必须确认它是可重跑任务。 |
| s5 | 验证阻塞解除：等待队列清空、报工 SQL 恢复流转 | 再跑一遍 SHOW FULL PROCESSLIST，确认 Waiting 状态消失。 |
| s6 | 业务侧确认报工恢复 | curl MES 健康接口看 db 状态和插入耗时，再让车间实际提交一笔验证。 |
| s7 | 防复发：把 ERP 重报表挪出生产高峰，进凌晨调度窗口 | crontab -e 把报表任务挪到凌晨窗口，从机制上让重查询与生产高峰错开。 |

每一步的判定命令见第 6 节的验收正则。

## 6. 验收标准（可机器判定）

判分方式：终端实操逐条比对命令正则（任一条命中即通过该步），最终按通过步数给出评级。

| # | 步骤目标 | 命中的命令正则 |
| --- | --- | --- |
| s1 | 先确认数据库服务活着，排除宕机 | `^systemctl\s+status\s+mysqld` 或 `^mysqladmin\s+ping` |
| s2 | 查看当前所有连接与正在执行的 SQL，找异常长查询 | `^mysql\b.*processlist` 或 `SHOW\s+(FULL\s+)?PROCESSLIST` |
| s3 | 确认阻塞链：谁堵谁、堵了多少会话 | `^mysql\b.*(innodb_trx|schema_table_lock_waits|INNODB\s+STATUS)` 或 `SHOW\s+ENGINE\s+INNODB` |
| s4 | 评估后终止阻塞源头（报表可重跑，业务优先） | `^mysql\b.*KILL\s+(QUERY\s+)?4213` 或 `^KILL\s+(QUERY\s+)?4213` |
| s5 | 验证阻塞解除：等待队列清空、报工 SQL 恢复流转 | `^mysql\b.*processlist` 或 `SHOW\s+(FULL\s+)?PROCESSLIST` |
| s6 | 业务侧确认报工恢复 | `^curl\b.*(mes|health|8080)` |
| s7 | 防复发：把 ERP 重报表挪出生产高峰，进凌晨调度窗口 | `^crontab\b` 或 `^mysql\b.*event` 或 `^vi\b.*cron` |

## 7. 常见错误与排查提示

- 先确认数据库服务活着，排除宕机：mysqladmin ping 是最快的存活探测。
- 要点：数据库活着、资源不紧张，但业务全卡——典型的「库没死，路被堵」。方向直指锁等待或长事务阻塞，下一步进数据库内部看会话。
- 查看当前所有连接与正在执行的 SQL，找异常长查询：mysql -e "SHOW FULL PROCESSLIST"，重点看 Time 特别大的和 State 为 Waiting 的会话。
- 要点：病灶清晰：4213 号 ERP 月末大报表跑了 312 秒还没完，持有 reporting 表的元数据锁；而 MES 应用恰好在这个高峰想给 reporting 加索引（4318），被堵；后续所有报工 INSERT（4319/4320…）排队等 4318——一条报表 SQL 堵死了整条报工链路。
- 确认阻塞链：谁堵谁、堵了多少会话：查 sys.schema_table_lock_waits 或 performance_schema，MySQL 直接告诉你 blocking_pid 是谁。
- 要点：sys 视图把阻塞链摆得明明白白：blocking_pid=4213，甚至给出了处置命令。排障要靠证据链，不靠猜——这一步的截图就是后面 KILL 操作的依据。
- 评估后终止阻塞源头（报表可重跑，业务优先）：mysql -e "KILL QUERY 4213"。注意用 KILL QUERY（只杀这条 SQL、保留连接），并且杀之前必须确认它是可重跑任务。
- 要点：KILL 前先过三关：它是什么（报表）、能不能杀（可重跑）、谁说了算（ERP 管理员确认）。KILL QUERY 只终止当前语句不断连接，比 KILL 4213 温和。生产数据库上的每一次 KILL 都应该有确认记录。
- 验证阻塞解除：等待队列清空、报工 SQL 恢复流转：再跑一遍 SHOW FULL PROCESSLIST，确认 Waiting 状态消失。
- 要点：26 个积压会话瞬间泄洪。注意 4318 的加索引操作还在跑——它也是高峰期的不当操作，索引变更应该放在维护窗口，这笔账复盘时一起算。
- 业务侧确认报工恢复：curl MES 健康接口看 db 状态和插入耗时，再让车间实际提交一笔验证。
- 要点：数据库指标正常 + 业务实测通过，故障才算关闭。卡死期间车间用纸质单记录的产量要盯紧补录，防止两天后对账出现空洞——故障恢复的收尾永远包含数据完整性检查。
- 防复发：把 ERP 重报表挪出生产高峰，进凌晨调度窗口：crontab -e 把报表任务挪到凌晨窗口，从机制上让重查询与生产高峰错开。
- 要点：这次事故是三方合谋：ERP 高峰跑大报表 + MES 高峰做 DDL + 没有阻塞告警。杀会话只是止血，调度错峰、变更窗口、监控告警三件事落地了，同类故障才会真正消失。
- 用 systemctl stop mysqld 解阻塞：会把 MES 业务一起打停，站内危险命令清单会拦截
- kill 错会话：先确认阻塞链再动手

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：SHOW PROCESSLIST 全量、当前活动会话数、慢查询数量
- 造故障：开一个长事务并持有锁（模拟 ERP 重报表），制造等待队列
- 记录回滚点：被终止会话的 id 与 SQL 文本

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- 先确认数据库服务活着，排除宕机
- 查看当前连接与正在执行的 SQL，找出异常长查询
- 用 information_schema.innodb_trx 确认阻塞链：谁堵谁、堵了多少会话
- 评估后终止阻塞源头（KILL 会话，不是 KILL 掉整个 mysqld）
- 验证等待队列清空、报工 SQL 恢复流转，再做防复发调度调整（把报表挪到凌晨窗口）
- 验收正则覆盖：服务状态 / PROCESSLIST / 阻塞链查询 / KILL / 验证 / 调度调整

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。
- 失败处理：上游模型不可用 → 明确提示「AI 暂时不可用」，并保留手工执行入口；文档缺失 → 明确提示「该题文档缺失」；命令执行失败 → 原样回显报错行并停止该步；环境不符（例如题目要求 MySQL 却连的是 PostgreSQL）→ 在执行前就提示不匹配，不静默继续。
- 本题涉及的判据一律以第 6 节的机器判据为准，不采信模型自述的「已完成」。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
