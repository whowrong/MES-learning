# 磁盘还有 40G 却写不进去：inode 被小文件吃光

## 1. 题目目标与业务背景

**目标**：识别这是 inode 耗尽而不是空间耗尽，定位吃 inode 的目录，安全清理小文件并验证写入恢复。

**背景**：MES 归档服务把每条报工快照落成一个小文件到 /data/archive，按天分目录。数据盘 /data 是 200G 的数据盘，平时用量很轻。

**现象**：今天报工写入开始报 "No space left on device"，但 df -h 显示 /data 还有 40G 空闲，运维一脸困惑。

## 2. 涉及的数据表或服务

- mes-archiver（报工归档服务）
- /data/archive（按天分目录的小文件归档区）
- 文件系统 inode 表

## 3. 需要的账号与权限

- 需要 sudo：可读写 /data/archive、可执行 find/rm、可查 mes-archiver 服务状态
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置 /data/archive/2026-10-xx 若干目录，每个目录放数千个小文件（模拟快照），把 inode 用量顶到 95% 以上
- 磁盘字节用量保持在 40% 左右（关键：空间没满，inode 满了）
- 归档目录按天分层，清理策略为保留 14 天

## 7. 常见错误与排查提示

- 先看 df -h：空间确实没满：df -h 看各分区空间用量。
- 要点：第一步永远是看全局：空间没满却报 No space left，说明问题不在字节数上。
- 改看 inode 使用率：df -i 看 inode 使用率，这是 inode 耗尽的确认命令。
- 要点：df -i 一眼看穿：IUse% 100%，而字节数还有 138G 可用——典型的 inode 耗尽。
- 定位吃 inode 的目录（按 inode 数排序）：用 du --inodes 按 inode 数排序，或 find 数文件个数。
- 要点：inode 是「小文件杀手」：每个文件至少占一个 inode，几百万个小文件能把 inode 表吃光而字节数几乎不动。
- 清理过期归档（只删归档目录、只删过期日期）：只清理 14 天以前的归档目录，用 find -mtime +14 精确圈定，不要 rm -rf /data/archive/*。
- 要点：清理必须带时间与路径双重限定：find -mtime +14 只动过期目录，路径写死，避免误删当天数据。
- 验证 inode 已释放：再跑一次 df -i 确认 IUse% 降下来。
- 要点：清理后必须复测，否则无法证明问题真的解决了。
- 验证归档写入恢复：写一个测试文件再删掉，确认能写。
- 要点：写入恢复才是最终验收：df 好看不等于系统能写。
- 只跑 df -h 就下结论：必须 df -i 才能看出 inode 耗尽
- rm -rf /data/archive/* 整目录清空：会把当天数据一起删掉，必须带 -mtime 限定

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：df -h /data 与 df -i /data 两组数据（对比着看差异）
- 造故障：批量 touch 大量小文件直到 IUse% ≥ 95%
- 确认现象：写入报 No space left on device，但 df -h 显示还有大量可用空间
- 记录回滚点：待清理目录清单与保留策略（14 天）

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- df -h 与 df -i 对比，确认是 inode 耗尽而不是空间耗尽
- du --inodes -x -d2 /data 定位吃 inode 的目录
- find /data/archive -type d -mtime +14 -exec rm -rf {} + 精确清理过期归档
- df -i 复测 + touch 测试文件验证写入恢复

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 模式 B 的容器里没有 systemd 与数据库服务；练 systemd 启停、日志轮转、备份定时任务这类步骤请用模式 A。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
