# 连接池被打满：报工接口大面积超时

- 题目编号：`lx-d10`
- 所属模块：运维实操营 · Linux 服务器实操
- 题目类型：运维实操（终端实操，真实服务器执行命令）
- 难度 / 建议时长：进阶 / 10 分钟
- 文档路径：`public/content/labs/lx-d10.md`（站内地址 `/content/labs/lx-d10.md`）

> 本文同时服务两类读者：人（讲清这道题在练什么、环境要求、步骤、验收、常见错法）与站内 AI（据此生成准备与执行脚本）。AI 生成的脚本一律先预览、再由用户确认执行。

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 1. 题目目标与业务背景

**目标**：定位是哪个会话占着连接不放，安全释放它，验证报工恢复，并把连接池与慢查询两处都补上防护。

**背景**：MES 报工接口服务 mes-report-api 用 HikariCP 连接 MySQL，连接池上限 20。库里有条 ERP 重报表查询经常跑十几分钟。

**现象**：上午 10 点开始，车间终端提交报工大面积超时，应用日志刷 "connection pool exhausted"，数据库连接数打满。

## 2. 涉及的数据表或服务

- mes-report-api（报工接口，HikariCP 连接池上限 20）
- MySQL 8.0（业务库）
- ERP 重报表长查询（占用连接的源头）

## 3. 需要的账号与权限

- 需要 sudo 管理应用服务；数据库演练账号需 PROCESS 与 KILL 会话权限（不要给超级管理员）
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置一条长时间运行的重报表查询（持有未提交事务）
- 连接池上限预置为 20，模拟被打满
- 预置报工接口端口（如 8093）与健康检查
- 数据库连接数上限设为 100 以上，便于观察连接回落

### 4.3 破坏性提示

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 6. 验收标准（可机器判定）

判分方式：终端实操逐条比对命令正则（任一条命中即通过该步），最终按通过步数给出评级。

| # | 步骤目标 | 命中的命令正则 |
| --- | --- | --- |
| s1 | 从应用日志确认是连接池耗尽 | `^journalctl\b.*-u\s+mes-report-api` 或 `^grep\b.*pool` 或 `^tail\b.*mes-report-api.*\.log` |
| s2 | 查数据库侧连接与正在执行的 SQL | `^mysql\b.*show\s+processlist` 或 `^mysql\b.*show\s+status` 或 `^mysql\b.*information_schema` |
| s3 | 确认阻塞/长事务的来源与影响面 | `^mysql\b.*innodb_trx` 或 `^mysql\b.*show\s+engine` 或 `^mysql\b.*show\s+processlist` |
| s4 | 终止阻塞源头会话（只 kill 那一条会话） | `^mysql\b.*kill\b` |
| s5 | 调整连接池上限并重启服务 | `^grep\b.*maximum-pool-size|^grep\b.*pool` 或 `^sed\b.*pool|^vi\b.*application` 或 `^systemctl\s+restart\s+mes-report-api` |
| s6 | 验证报工恢复且连接数回落 | `^mysql\b.*show\s+status` 或 `^curl\s` 或 `^journalctl\b.*-u\s+mes-report-api` |

## 7. 常见错误与排查提示

- 从应用日志确认是连接池耗尽：journalctl -u 看应用自己报什么。
- 要点：应用日志先给方向：连接池取不到连接，是「连接不够用」而不是「数据库挂了」。
- 查数据库侧连接与正在执行的 SQL：mysql -e 'SHOW FULL PROCESSLIST' 看谁在跑。
- 要点：20 条连接正好等于连接池上限，而且其中一条已经跑了 982 秒——线索就在这条长查询上。
- 确认阻塞/长事务的来源与影响面：information_schema.innodb_trx 看未提交事务与线程 id。
- 要点：把「长查询」升级成「未提交长事务」：它不只是慢，还在占着连接和锁。
- 终止阻塞源头会话（只 kill 那一条会话）：KILL 具体的 thread id，不要重启整个 mysqld。
- 要点：KILL 单条会话是精准止血；重启数据库会把 MES 业务一起打断，属于事故扩大。
- 调整连接池上限并重启服务：备份配置后调大池上限，再重启服务。
- 要点：池太小会在负载高峰被瞬时打满；放大到 50 是给短时峰值留余量，同时靠慢查询治理治本。
- 验证报工恢复且连接数回落：确认连接数回落、报工接口 200、日志不再刷连接池错误。
- 要点：三条证据齐了才算处置完成：连接数回落、接口可用、错误不再出现。
- 用 systemctl restart mysqld 解阻塞：会把 MES 业务一起打断，站内危险清单会拦截
- kill 错会话：先确认阻塞链再动手

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：journalctl -u 应用日志、SHOW FULL PROCESSLIST、Threads_connected
- 造故障：开启长事务并让应用并发请求把连接池打满
- 记录回滚点：被杀会话的 id 与 SQL 文本、配置文件 .bak 副本

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- journalctl -u 确认连接池耗尽错误
- SHOW FULL PROCESSLIST 与 innodb_trx 定位长事务与其 thread id
- KILL 该会话精准止血（不重启 mysqld）
- 备份并调大 maximum-pool-size，重启应用
- 验证：Threads_connected 回落 + 报工接口 200 + 日志无连接池错误

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
