# 大型综合：整套 MES 演练环境上线、故障注入与回滚

- 题目编号：`lx-d11`
- 所属模块：运维实操营 · Linux 服务器实操
- 题目类型：运维实操（终端实操，真实服务器执行命令）
- 难度 / 建议时长：综合 / 45 分钟
- 文档路径：`public/content/labs/lx-d11.md`（站内地址 `/content/labs/lx-d11.md`）

> 本文同时服务两类读者：人（讲清这道题在练什么、环境要求、步骤、验收、常见错法）与站内 AI（据此生成准备与执行脚本）。AI 生成的脚本一律先预览、再由用户确认执行。

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 1. 题目目标与业务背景

**目标**：按「盘点 → 部署 → 反代 → 监控 → 注入排查 → 端到端验收 → 回滚演练 → 交付清单」八个阶段完成整场演练，每阶段都有可机器判定的验收命令。

**背景**：你要在一台演练机上从零交付一套 MES 最小可用环境：MySQL 业务库 + 一个可离线部署的小型 Web 服务（报工看板）+ nginx 反向代理 + 健康检查与监控脚本，并交付一份可回滚的上线记录。

**现象**：交付窗口内，运维方会随机注入 1–2 个故障（磁盘写满、证书过期、数据库连接池耗尽、权限不足、备份为空）。你需要定位、修复、验证，并保证任何一步都能回滚到上一个版本。

## 2. 涉及的数据表或服务

- MySQL 8.0 演练实例（容器 mes-mysql，端口 3307）
- mes-board（离线部署的小型 Web 服务，systemd 托管）
- nginx（反向代理，监听 8099）
- health-check.sh 与 backup-db.sh（监控与备份脚本 + cron）

## 3. 需要的账号与权限

- 需要 sudo：可管理 systemd 服务、可写 /etc/nginx 与 /opt/mes、可操作 docker、可排 crontab
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 演练机需具备 Docker（用于一次性数据库实例）与 systemd；推荐 4 vCPU / 4–8 GB 内存 / 40 GB 磁盘
- 预置离线部署包 /opt/mes/dist/mes-board-1.0.0.tar.gz 与上一版本目录（供回滚演练）
- 预置 nginx、docker、python3、mysqldump 客户端
- 演练数据库与宿主既有服务端口隔离（容器映射到 3307）
- 监控与备份脚本通过 cron 调度，产物目录 /data/backup/db

### 4.3 破坏性提示

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

| --- | --- | --- |

## 7. 常见错误与排查提示

- 阶段一：盘点环境（规格、端口占用、已有服务）：nproc / free -h / df -h 看规格，ss -lntp 看端口占用。
- 要点：先盘点是硬规矩：规格不够就别开始部署，端口冲突先解决再装服务——否则后面的故障全是自己挖的坑。
- 阶段二：部署数据库并建库建表：docker run 起一个独立实例（端口 3307 避开宿主既有服务），再建表并验证。
- 要点：演练数据库必须与任何在用实例物理隔离：独立容器 + 独立端口 + 一次性口令，题目做完直接销毁。
- 阶段三：部署应用（离线包 + systemd 托管）：解包 → 建专用用户 → 改属主 → 单元托管。
- 要点：应用用专用系统用户运行并把属主给到它，是权限类故障的预防手段，也能让权限问题有明确责任边界。
- 阶段四：配置反向代理与健康检查：写站点配置 → nginx -t 校验 → reload → curl 验证。
- 要点：nginx -t 是改配置后的强制关卡：校验不过绝不 reload，否则整站可能起不来。
- 阶段五：部署监控与备份脚本（定时 + 可验证）：写健康检查与备份脚本，加执行权限并排 cron。
- 要点：备份脚本必须带「非空校验 + 原子改名」，健康检查脚本必须能被 crontab 调用——这两条是后面回滚与监控验收的依据。
- 阶段六：故障定位（对注入的故障取证）：按现象选择取证命令：df/du 看磁盘、journalctl 看服务日志、openssl 看证书、show processlist 看连接。
- 要点：故障注入点是多选一，先用现象定位属于哪一类，再深挖；取证要先于动手改。
- 阶段七：修复并保留证据（先备份再改）：任何修改前先备份证据与配置；修完立刻验证服务状态。
- 要点：修复动作要可回滚：备份文件与配置放在一起，证据留档（截图/日志片段），复盘时能还原现场。
- 阶段八：端到端验收（可用性 + 数据一致性）：健康检查、业务接口、数据查询、服务状态四条一起验。
- 要点：验收要覆盖四层：健康检查通、业务接口通、数据对得上、服务在运行——少一条都不算上线成功。
- 阶段九：回滚演练（回到上一个版本并验证）：停服务 → 回退配置/版本 → 起服务 → 验证。
- 要点：回滚必须真的演练过一次：没有验证过的回滚方案等于没有回滚方案——这是上线前最有价值的一次演练。
- 阶段十：交付验收清单：把十项验收逐条写成清单文件。
- 要点：交付物是可核查的清单，不是「已完成」三个字；逐条勾选，评审与复盘都有据可依。
- 跳过阶段一直接部署：规格与端口冲突会变成后面的「故障」
- 没有演练过回滚就宣称有回滚方案：回滚必须真实跑过一次并验证

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 阶段一：nproc / free -h / df -h / ss -lntp 记录规格与端口占用
- 阶段二：docker run 独立 MySQL 实例（3307）+ 建 work_report 表 + 插入基线数据
- 阶段三：解包到 /opt/mes/app + 建 mesapp 专用用户 + systemd 托管
- 阶段四：写 nginx 站点（8099，/health 健康检查）+ nginx -t + reload
- 阶段五：写 health-check.sh 与 backup-db.sh（临时文件 + 非空校验 + 原子改名）+ 排 cron
- 阶段六：按注入的故障类型准备证据（磁盘满 / 证书过期 / 连接池耗尽 / 权限不足 / 备份为空）
- 记录回滚点：所有被改配置先 cp 一份 .bak-20261030

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- 阶段六：先用现象取证（df/du、journalctl、openssl、show processlist），再动手修
- 阶段七：先备份再修复（truncate -s 0 / find -mtime -delete / chown / 改配置并备份），修完立刻 is-active 验证
- 阶段八：四层端到端验收：/health 200 + 业务接口 200 + 数据条数核对 + 三个服务 active
- 阶段九：真实回滚演练（stop → 回退 .bak/上一版本 → start → curl 验证 200）
- 阶段十：输出十项验收清单文件 /opt/mes/delivery/acceptance.md

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。
- 失败处理：上游模型不可用 → 明确提示「AI 暂时不可用」，并保留手工执行入口；文档缺失 → 明确提示「该题文档缺失」；命令执行失败 → 原样回显报错行并停止该步；环境不符（例如题目要求 MySQL 却连的是 PostgreSQL）→ 在执行前就提示不匹配，不静默继续。
- 本题涉及的判据一律以第 6 节的机器判据为准，不采信模型自述的「已完成」。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
