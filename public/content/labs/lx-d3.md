## 1. 题目目标与业务背景

**目标**：找出占用 9100 的进程，确认其身份并规范处置，让新服务正常上线。

**背景**：今天要在这台服务器部署新的 MES-ERP 接口桥接服务（mes-erp-bridge，监听 9100）。

**现象**：systemctl start 后服务立即退出，日志报 java.net.BindException: Address already in use。

## 2. 涉及的数据表或服务

- mes-erp-bridge（待上线的 MES-ERP 桥接服务，监听 9100）
- 占用 9100 的历史遗留脚本进程

## 3. 需要的账号与权限

- 需要 sudo：可查端口占用（ss / lsof）、可终止遗留进程、可启动新服务
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置一个监听 9100 的遗留进程（nc -lk 9100 或旧脚本），并让它看起来像业务遗留
- 预置 mes-erp-bridge.service（停止状态），启动后日志报 Address already in use
- 9100 之外的端口保持空闲，避免干扰判断

## 7. 常见错误与排查提示

- 查 9100 端口被哪个进程占用：ss -lntp 或 netstat -tlnp 列出监听端口和进程，grep 9100 过滤。
- 要点：Address already in use 的排查铁三角：谁在监听（ss/netstat/lsof 任选其一）。占用者是 pid 4321 的一个 python3 进程。
- 查清这个进程的身份：是什么、谁启动的：ps -fp 4321 查看进程详情，注意启动时间和命令行。
- 要点：两年前前任手敲 nohup 启动的旧同步脚本，没有文档、不在服务列表。这种「幽灵进程」是小厂服务器的常态——先搞清楚它干什么，再决定去留。
- 与相关方确认该脚本已废弃后，优雅终止它：kill -15 4321 发送优雅终止信号，给它机会写完手头的数据。
- 要点：默认 -15（SIGTERM）让进程自己收尾；-9（SIGKILL）是内核直接抹掉，临时文件和未发送的数据全丢。先礼后兵，-9 只留给杀不死的。
- 启动新的桥接服务：systemctl start mes-erp-bridge。
- 要点：端口腾出来后一次启动成功。对比之前反复 BindException——绑定失败的排查关键从来不在新服务本身，而在占用者。
- 验证 9100 已由新服务接管并正常监听：再跑一遍 ss -lntp | grep 9100，确认监听者已经换成 java(8811)。
- 要点：同一个端口，占用者从 python3(4321) 换成 java(8811)，健康检查 UP——端口交接完成。上线动作永远以「验证」收尾，不以「启动」收尾。
- 看到端口占用就 kill -9：要先确认身份，避免杀掉还在用的业务进程
- kill 掉新服务而不是遗留进程：判定依据是进程身份，不是端口号

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- 用 ss -lntp（或 lsof -i:9100）确认 9100 被谁占着
- 用 ps -fp <pid> / cat /proc/<pid>/cmdline 查清进程身份，再决定处置方式
- 确认该脚本已废弃后用 kill（先 TERM，必要时再 KILL）优雅终止
- 启动 mes-erp-bridge，用 ss 确认 9100 已由新服务接管并监听
- 验收正则覆盖：端口查询 / 身份确认 / 终止 / 启动 / 监听验证
