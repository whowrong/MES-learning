# 磁盘打满：MES 采集服务停止写库

- 题目编号：`lx-d1`
- 所属模块：运维实操营 · Linux 服务器实操
- 题目类型：运维实操（终端实操，真实服务器执行命令）
- 难度 / 建议时长：入门 / 10 分钟
- 文档路径：`public/content/labs/lx-d1.md`（站内地址 `/content/labs/lx-d1.md`）

> 本文同时服务两类读者：人（讲清这道题在练什么、环境要求、步骤、验收、常见错法）与站内 AI（据此生成准备与执行脚本）。AI 生成的脚本一律先预览、再由用户确认执行。

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 1. 题目目标与业务背景

**目标**：定位吃掉磁盘的大文件，安全清理释放空间，恢复采集服务，全程不丢报工数据。

**背景**：某机械厂 MES 数据采集服务（mes-collector，Java）负责接收车间终端的报工数据并写库，部署在这台 CentOS 服务器上。

**现象**：09:40 起车间终端集体提示「提交失败」，采集服务日志报 java.io.IOException: No space left on device。

## 2. 涉及的数据表或服务

- MES 采集服务 mes-collector（Java 进程，持续写 /var/log/mes-collector.log）
- systemd（服务启停与状态）
- 本地文件系统（根分区与 /data 数据盘）

## 3. 需要的账号与权限

- 需要 sudo 权限：可读 /var/log、可执行 truncate / du / df、可 restart mes-collector.service
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- systemd 可用，预置 mes-collector.service（运行中）并让它持续写日志
- 根分区使用率 ≥ 95%（模拟打满），/data 等其它分区 ≤ 40%，避免误判是哪块盘满了
- 预置一个 ≥ 1 GB 的 mes-collector.log（用 fallocate -l 1G 生成即可，不要真造 35 G）
- 预置另一个正常服务，确保学员不会为了腾空间去动无关服务

### 4.3 破坏性提示

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 6. 验收标准（可机器判定）

判分方式：终端实操逐条比对命令正则（任一条命中即通过该步），最终按通过步数给出评级。

| # | 步骤目标 | 命中的命令正则 |
| --- | --- | --- |
| s1 | 查看各分区使用情况，确认哪个分区满了 | `^df\b` |
| s2 | 从根目录逐层收敛，找出占用最大的目录 | `^du\s.*(--max-depth|-s|-h|-x)` |
| s3 | 深入 /var，确认具体是哪个子目录 | `^du\b.*/var` 或 `^ls\b.*/var/log` |
| s4 | 安全清空正在被进程写入的大日志（不能直接删） | `^truncate\s+-s\s*0\b.*mes-collector` 或 `^cat\s+/dev/null\s*>.*mes-collector` 或 `^>\s*/var/log/mes-collector` |
| s5 | 确认空间已释放 | `^df\b` |
| s6 | 恢复采集服务并确认运行状态 | `^systemctl\s+(restart|start)\s+mes-collector` |

## 7. 常见错误与排查提示

- 查看各分区使用情况，确认哪个分区满了：查看磁盘分区使用量的命令，两个字母，d 开头。
- 要点：排障第一步永远先看全局。df 显示根分区 100%，而 /data 数据盘才 31%——问题在系统盘，先别动数据库。
- 从根目录逐层收敛，找出占用最大的目录：统计目录占用的命令是 du，配合 -h（人类可读）和 --max-depth=1（只看一层）或 -sh。
- 要点：du 逐层收敛范围：/var 占了 46G。日志、缓存、临时文件都在 /var 下，这是最常见的磁盘杀手。
- 深入 /var，确认具体是哪个子目录：继续用 du 或 ls 深入 /var 的子目录，重点看 /var/log。
- 要点：定位到 mes-collector.log 单文件 35G——采集服务的日志没有任何轮转策略，两年写了 35G。这就是根因。
- 安全清空正在被进程写入的大日志（不能直接删）：对正在被写入的日志文件，用 truncate -s 0 或重定向清空，而不是 rm。
- 要点：进程正持有日志文件句柄时用 rm 删除，磁盘块不会释放，df 依然显示满——必须重启进程才生效。truncate 原地清空才是正解。
- 确认空间已释放：清理完再跑一遍第 1 步的命令，确认 Use% 降下来了。
- 要点：根分区从 100% 降到 30%。清理后必须验证，不能清完就走——万一清错了地方，这一步能立刻发现。
- 恢复采集服务并确认运行状态：systemd 管理的服务用 systemctl restart 重启，服务名 mes-collector。
- 要点：磁盘满时服务已异常停止，空间释放后重启拉起。status 显示 active (running) 才算恢复，光 restart 不确认等于没修。
- 直接 rm 正在写入的日志：空间不释放，必须 truncate -s 0
- 把 /var/log 下的别的文件一起清掉：清之前先 du 确认路径，只清目标文件

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：df -h 各分区使用率、/var/log 下文件清单与大小
- 造故障：fallocate -l 1G /var/log/mes-collector.log 并确认 df 使用率 ≥ 95%
- 确认故障现象：systemctl status mes-collector 正常但写日志时报 No space left on device
- 记录回滚点：待清理文件清单、原始大小与恢复方式

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- 先 df -h 定位满的分区，再 du -h --max-depth=1 / 逐层收敛，最后 du -h /var/log 定位到具体文件
- 清理正在写入的日志用 truncate -s 0（rm 不释放空间，因为进程仍持有文件句柄）
- 清理后再跑一次 df -h 验证使用率下降，然后 systemctl restart mes-collector 并确认 active
- 验收正则：df / du / truncate / systemctl 四类都要命中，缺一步都不算通过

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。
- 失败处理：上游模型不可用 → 明确提示「AI 暂时不可用」，并保留手工执行入口；文档缺失 → 明确提示「该题文档缺失」；命令执行失败 → 原样回显报错行并停止该步；环境不符（例如题目要求 MySQL 却连的是 PostgreSQL）→ 在执行前就提示不匹配，不静默继续。
- 本题涉及的判据一律以第 6 节的机器判据为准，不采信模型自述的「已完成」。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
