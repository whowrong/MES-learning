# 备份文件是 0 字节：昨晚的库备份没成

- 题目编号：`lx-d9`
- 所属模块：运维实操营 · Linux 服务器实操
- 题目类型：运维实操（终端实操，真实服务器执行命令）
- 难度 / 建议时长：进阶 / 10 分钟
- 文档路径：`public/content/labs/lx-d9.md`（站内地址 `/content/labs/lx-d9.md`）

> 本文同时服务两类读者：人（讲清这道题在练什么、环境要求、步骤、验收、常见错法）与站内 AI（据此生成准备与执行脚本）。AI 生成的脚本一律先预览、再由用户确认执行。

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 1. 题目目标与业务背景

**目标**：查明备份变空的原因（磁盘满 + 重定向覆盖），恢复可用备份，并加上「失败不覆盖旧文件」的保护。

**背景**：MES 业务库每天 01:30 由 /opt/mes/scripts/backup-db.sh 备份到 /data/backup/db/，保留 14 天，脚本把标准输出重定向到目标文件。

**现象**：今早例行检查发现 db-2026-10-29.sql 是 0 字节，而前几天的备份都正常有几 GB。

## 2. 涉及的数据表或服务

- backup-db.sh（备份脚本）
- MySQL（业务库 mes_prod）
- /data/backup/db（备份产物目录）

## 3. 需要的账号与权限

- 需要 sudo 或备份账号：可读脚本与日志、可写 /data/backup/db、可执行 mysqldump
- SSH 私钥 / 口令只保存在本站服务端，不进仓库、不进文档。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 演练服务器最低配置：2 vCPU / 2 GB 内存 / 20 GB 可用磁盘（其中日志分区 ≥ 2 GB）；Debian 12 或 Ubuntu 22.04 及以上，需 systemd
- 演练服务器推荐配置：4 vCPU / 4–8 GB 内存 / 40 GB 可用磁盘（日志分区 ≥ 10 GB）；Debian 13 或 Ubuntu 24.04，Docker 29 可用
- 系统版本：Debian GNU/Linux 12/13 或 Ubuntu 22.04/24.04（systemd + bash + coreutils）

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

- 预置备份脚本使用 > 直接重定向到目标文件（失败即产生 0 字节文件）
- 预置 /data/backup/db 中若干正常历史备份与一份 0 字节的最新备份
- 磁盘 /data 使用率顶到 100%（备份目录占大头）
- 演练 MySQL 账号可用（本机 127.0.0.1:3306 或独立演练实例）

### 4.3 破坏性提示

> ⚠️ 本站演练会执行删除、重建、清库、杀进程、改防火墙、重启服务等破坏性操作。请只填**可破坏、演练专用**的数据库与服务器；生产环境、重要数据环境请勿填入。建议用一次性实例，或随时能从快照重建的环境。

## 6. 验收标准（可机器判定）

判分方式：终端实操逐条比对命令正则（任一条命中即通过该步），最终按通过步数给出评级。

| # | 步骤目标 | 命中的命令正则 |
| --- | --- | --- |
| s1 | 看备份目录，确认哪些文件是空的 | `^ls\b.*-l` 或 `^find\b.*-size\s*0` |
| s2 | 查备份脚本与它的日志 | `^cat\b.*backup-db` 或 `^ls\b.*backup.*\.log|^tail\b.*backup.*\.log` 或 `^grep\b.*backup` |
| s3 | 确认磁盘满的真实原因 | `^df\b` 或 `^du\b.*--max-depth` 或 `^du\b.*-h` |
| s4 | 清理过期备份（只删 14 天以前的） | `^find\b.*-mtime` 或 `^rm\b.*backup` 或 `^find\b.*-delete` |
| s5 | 修脚本：先写临时文件、成功后再改名 | `^cat\b.*>.*\.tmp|^cp\b` 或 `^sed\b.*backup-db` 或 `^vi\b.*backup-db` 或 `^python3?\b.*backup` |
| s6 | 补跑备份并验证产物可用 | `^/opt/mes/scripts/backup-db\.sh|^bash\b.*backup-db` 或 `^ls\b.*-lh.*backup` 或 `^gzip\b.*-t|^head\b.*\.sql` 或 `^mysql\b.*<` |

## 7. 常见错误与排查提示

- 看备份目录，确认哪些文件是空的：ls -lh 看大小，find -size 0 精确找出空文件。
- 要点：先量化问题：只有最新那份是 0 字节，说明脚本还在跑，但产出为空。
- 查备份脚本与它的日志：看脚本怎么写的、日志里报了什么。
- 要点：根因有两个叠加：磁盘满 + 脚本用 > 直接重定向到目标文件——命令失败后目标文件已经被创建并清空，看起来像「备份成功但是空的」。
- 确认磁盘满的真实原因：df -h 确认满了，再 du 看是哪块占的。
- 要点：磁盘 100% 是表象：118G 全在备份目录里，是备份从来没清理过旧文件。
- 清理过期备份（只删 14 天以前的）：find -mtime +14 精确圈定过期备份再删。
- 要点：保留策略要落到命令上：只删超过保留期的文件，绝不 rm -rf 整个目录。
- 修脚本：先写临时文件、成功后再改名：改成先写 .tmp、校验非空后再 mv 成正式文件。
- 要点：「写临时文件 + 非空校验 + 原子改名」是备份脚本的标准写法：失败时旧文件还在，不会出现 0 字节备份覆盖好数据。
- 补跑备份并验证产物可用：补跑一次，再 ls 确认非空、head 确认内容像 dump。
- 要点：备份完成的判据是「文件非空且内容像 dump」，不是「脚本退出码为 0」。
- rm -rf 整个备份目录释放空间：会毁掉历史可用备份
- 只看脚本退出码就判定备份成功：必须校验文件非空且内容像 dump

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 记录基线：ls -lh 备份目录、df -h /data、tail 备份日志、du --max-depth=1 /data
- 造故障：把磁盘占满并手动跑一次脚本产生 0 字节文件
- 记录回滚点：脚本 .bak 副本、待清理的过期备份清单

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- ls -lh + find -size 0 定位空备份
- cat 脚本 + tail 日志确认根因（磁盘满 + > 覆盖）
- df -h + du 定位占用目录
- find -mtime +14 精确清理过期备份释放空间
- 改脚本为「临时文件 + 非空校验 + 原子改名」并补跑
- ls 非空 + head 校验内容像 dump

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。
- 失败处理：上游模型不可用 → 明确提示「AI 暂时不可用」，并保留手工执行入口；文档缺失 → 明确提示「该题文档缺失」；命令执行失败 → 原样回显报错行并停止该步；环境不符（例如题目要求 MySQL 却连的是 PostgreSQL）→ 在执行前就提示不匹配，不静默继续。
- 本题涉及的判据一律以第 6 节的机器判据为准，不采信模型自述的「已完成」。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一台可 SSH 登录的 Linux 主机（演练专用，别用生产机）
- 能执行 systemctl / journalctl / df / du / find 等命令的账号
- sudo 权限（部分步骤要停服务、改配置、重启）
- 主机名不要含 prod / 生产 / 正式 / 线上，否则站内会红色告警并要求二次确认

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 sshd 容器（账号 lab、随机口令；端口 14300-14349 段，现场生成，只回显一次）
- 干净的系统盘与数据目录：没有预置脏数据
- 容器内只有基础命令（df / du / find / touch / rm 等），没有 systemd，也没有数据库服务

- 最小组件配置：1 vCPU / 512 MiB 内存 / 2 GiB 可用磁盘
- 推荐配置：2 vCPU / 1 GiB 内存 / 5 GiB 可用磁盘（inode 占用类题目建议 1 GiB 以上 inode 配额）

**模式 B 的限制：**

- 本题第 4.2 节要求预置 systemd 服务 / 数据库服务 / 业务进程，模式 B 的一次性容器里没有这些服务——这类步骤请用模式 A，或在模式 A 的机器上预置后再练。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
