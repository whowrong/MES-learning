- 难度 / 建议时长：入门 / 6 分钟

## 1. 题目目标与业务背景

**目标**：把 work_orders 里 status 为「已完成」或「完成」的记录统一改成 Completed。执行成功后提交校验。

**业务背景**：work_orders 的 status 里混着中文「已完成」「完成」和英文「Completed」——三个值一个意思。每次出报表都要 IN 三个值，早晚有人漏写。治理动作：统一成标准值 Completed。

## 2. 涉及的数据表或服务

- 涉及表：`work_orders`
- 练习库结构：内置练习库共 8 张表（items / bom / employees / equipment / work_orders / work_reports / inventory / sales_orders），合计约 231 行；真实连库时按第 4 节的空间与数据量建议预置同量级数据。

## 3. 需要的账号与权限

- 需要目标表的 SELECT 与写权限（INSERT/UPDATE/DELETE）。建议用演练账号授权到库级，不要用 DBA 账号。
- 连接信息只保存在本站服务端（页面与仓库都不落明文密码），列表回显一律脱敏。

## 4. 环境要求（演练专用）

### 4.1 规格基线

- 数据库版本：MySQL 8.0.x / MariaDB 10.11 / PostgreSQL 15 及以上；站内内置练习库由 node:sqlite 提供，SQL 走 SQLite 兼容子集
- 最小表空间 / 数据量：数据库可用空间 ≥ 100 MB；数据量按内置练习库同量级预置（8 张表、约 231 行），单题新增脏数据 ≤ 200 行

> 规格出处：以下数值对齐已验证过的目标机 instabox dev 实测规格（4 vCPU / 7.8 GiB 内存、根分区 16 GB + 数据盘 20 GB、Debian GNU/Linux 13，内核 6.18，Docker 29.8 可用），最低配置按其一半左右给出，保证题目脚本与路径在演练机上跑得通。

### 4.2 额外要求

## 5. 标准步骤

```sql
UPDATE work_orders SET status = 'Completed' WHERE status IN ('已完成','完成')
```

- 思路提示：先 GROUP BY status 看清现状有几种写法，再 UPDATE 归一
- 讲解：清洗前先跑 GROUP BY 摸清字段的全部取值分布，是数据体检的标准动作——你以为只有三种写法，实际可能还有 completed（小写）和「已 完成」（带空格）。归一之后要做的更重要：在系统里把 status 改成枚举/字典约束，让脏数据再也进不来。清洗解决存量，约束解决增量。

## 6. 验收标准（可机器判定）

判分方式：按状态判定——执行你的 SQL 后重新跑校验 SQL，取状态类字段与期望值比对。

```sql
SELECT COUNT(*) AS n FROM work_orders WHERE status IN ('已完成','完成')
```

- 期望结果：`[[0]]`

## 7. 常见错误与排查提示

- 常见错法：先 GROUP BY status 看清现状有几种写法，再 UPDATE 归一
- 为什么：清洗前先跑 GROUP BY 摸清字段的全部取值分布，是数据体检的标准动作——你以为只有三种写法，实际可能还有 completed（小写）和「已 完成」（带空格）。归一之后要做的更重要：在系统里把 status 改成枚举/字典约束，让脏数据再也进不来。清洗解决存量，约束解决增量。

## 8. AI 环境准备步骤（供站内 AI 生成准备脚本）

AI 应当按下面的顺序在**用户填写的演练环境**上生成准备脚本；每条命令都必须先预览、由用户确认后再执行，命中站内危险命令清单的一律二次确认。

- 确认连接可达：先跑一条只读查询（如 `SELECT 1`）确认账号、库名、网络都通。
- 确认目标表存在且结构一致：跑 `SHOW COLUMNS` / `\d` 之类只读命令核对字段名与类型。
- 预置脏数据：按本题的场景补齐需要的脏数据行（脏值、多写法状态值、尾部空格等），并记录补了多少行以便回滚。
- 记录基线：把关键表的行数与关键汇总值（本题校验 SQL 的期望值）先查一遍存下来，作为回滚与验收基准。

## 9. AI 执行脚本要点（供站内 AI 生成执行脚本）

- 先跑只读校验：`SELECT COUNT(*) AS n FROM work_orders WHERE status IN ('已完成','完成')`
- 再跑用户的作答 SQL，并把结果与校验 SQL 的期望值比对；不一致要指出差在哪一行、差多少。
- 涉及写操作（UPDATE/DELETE）时，先用 SELECT 预览受影响的行数，确认行数与预期一致再提交。

## 10. 安全边界与失败处理

- 只在用户自己提供的演练环境上执行；不连接任何生产实例，也不改动本站服务端配置。
- 生成的脚本一律先给出预览，用户确认后才执行；危险命令走站内既有拦截清单与二次确认。
- 失败处理：上游模型不可用 → 明确提示「AI 暂时不可用」，并保留手工执行入口；文档缺失 → 明确提示「该题文档缺失」；命令执行失败 → 原样回显报错行并停止该步；环境不符（例如题目要求 MySQL 却连的是 PostgreSQL）→ 在执行前就提示不匹配，不静默继续。
- 本题涉及的判据一律以第 6 节的机器判据为准，不采信模型自述的「已完成」。

## 11. 两种演练环境模式下的准备要求

站内实操面板提供两种并列的执行环境：**模式 A（我的远程环境）** 与 **模式 B（站点的一次性 Docker 演练环境）**。
两种模式共用同一份题目文档、同一套 AI 脚本生成、预览与二次确认、危险命令拦截和判分口径，只有「命令打到哪里」这一层不同。

### 11.1 模式 A：使用我的远程环境

你提供自己部署的练习用数据库 / 服务器，站内 AI 按本文档生成准备与执行脚本，并在你那台机器上真实执行。

- 一个可登录的数据库账号（MySQL / PostgreSQL / SQL Server，与题目要求一致）
- 对目标库表的建表、写入、删除权限（本题含删除 / 重建 / 清库类步骤）
- 一个可丢弃的练习用库：不要指向生产库

- 优势：贴近真实交付环境（真实数据形态、真实账号权限），可长期复用为演练台；
- 代价：环境、账号、权限都要自己准备与维护。

### 11.2 模式 B：使用站点的一次性 Docker 演练环境

站点在部署机上起一个可丢弃的容器，演练结束或超时后自动销毁并释放端口；端口与随机口令现场生成、只回显一次，不进仓库、不进文档、不进日志。

**站点预置的内容：**

- 一次性 MySQL 8.0 容器（端口 14200-14249 段，现场生成；随机口令只回显一次，不落盘）
- 空库：建表 / 写入 / 索引重建类步骤可以从零做
- 容器内只有数据库本身，没有宿主机上的 systemd / nginx / 业务应用

- 最小组件配置：1 vCPU / 1 GiB 内存 / 2 GiB 可用磁盘（MySQL 8.0 实例约需 512 MiB 内存）
- 推荐配置：2 vCPU / 2 GiB 内存 / 5 GiB 可用磁盘（给 InnoDB 留 1 GiB buffer pool）

**模式 B 的限制：**

- 模式 B 的容器里只有数据库本身；依赖宿主机服务（systemd / nginx / 业务进程）的步骤请用模式 A。
- 模式 B 的容器是一次性的：演练结束或超时后自动销毁，容器里的数据不保留。

### 11.3 两种模式怎么选

- 反复练习、破坏性操作、想零准备随时开始 → 选模式 B；
- 正式交付前的真实环境验证、想保留数据与账号权限 → 选模式 A；
- 两者可混用：先在模式 B 把步骤练熟，再到模式 A 的机器上按同一份文档复跑一遍。
